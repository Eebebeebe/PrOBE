> Read-only diagnosis of how the Factorio 2.1.25 game data affects the editor, made on 2026-11-26 against commit 6afb768b. Seven diagnosticians each covered one area, and a skeptic re-checked every area against the code and both data files. Where they disagree, the "Skeptic" paragraph is the corrected reading. File:line references are from that commit. This is input for the 2.1 data migration in docs/PLAN.md, not a description of current behaviour.

# Factorio 2.1 data: diagnosis

## accepted-recipes

**Root cause:** Factorio 2.1 replaced the single RecipePrototype field `category` (a string, default "crafting") with `categories` (an array, default {"crafting"}, never empty). 2.1 also removed the 2.0 combined "X-or-Y" categories ("organic-or-assembling", "crafting-with-fluid-or-metallurgy", "electronics", "pressing", "basic-crafting" and so on) from the recipes and from the machines' crafting_categories. In the new data.json, none of the 656 recipes has a `category` key: 509 have `categories` and 147 have neither. Entity.acceptedRecipes (packages/editor/src/core/Entity.ts:393-401) still does `e.crafting_categories.includes(recipe.category || 'crafting')`. Because `recipe.category` is now always undefined, every recipe is treated as "crafting". As a result:

- assembling-machine-1, -2 and -3 accept all 656 recipes, including recycling, parameter, smelting and oil recipes.
- The other 14 crafting machines accept 0: oil-refinery, chemical-plant, centrifuge, biochamber, crusher, foundry, captive-biter-spawner, electromagnetic-plant, cryogenic-plant, rocket-silo, the three furnaces and the recycler.

That is why the corpus histogram's "value" bucket drops from 14366 to 5735. Most crafting machines in the blueprint corpus are furnaces, chemical plants and similar machines, and they now return an empty list. The data's `categories` arrays have up to 2 entries; the game crafts a recipe in a machine when any one of them is in the machine's crafting_categories. The game's API reference (Factorio/doc-html/prototype-api.json, RecipePrototype.categories) says: "The categories of this recipe. Controls which machines can craft this recipe ... The array must contain at least one category, it cannot be empty", default `{"crafting"}`. The bundled typed-factorio 3.36.0 types still describe the 2.0.75 API (`category?` plus `additional_categories?`), so the compiler never flagged the missing field. Entity.ts:1423 has the same stale field: `FD.recipes[tRecipe].category === 'crafting-with-fluid'` is now always false, so paste-settings never copies the direction of fluid recipes any more. That check already missed the 2.0 "crafting-with-fluid-or-metallurgy" recipes, which was an older bug. The entity side is unchanged in shape: crafting_categories is still an array, it is read by Entity.ts:1738, and it matches the 2.1 Lua.

**Fixed-point effects:** tests/**fixtures**/entity-accessors.json changes for acceptedRecipes. Before the fix, the 2.1 data's 'value' count is 5735: only assemblers return a list, holding all 656 recipes, and every other crafting machine returns empty. After the fix it should come back close to the 2.0 count of 14366, because furnaces, chemical plants, refineries and the Space Age machines return their lists again. Small differences are expected only from corpus entities whose prototype changed in 2.1. Any fixture or spec that records list contents or lengths will move:

- AM1 185->197
- AM2/AM3 229->230
- foundry and biochamber: same counts, but different names
- recycler 311->313

The browser fixture (tests/entity-accessors.spec.ts) and the headless one share the same JSON, so both need regenerating after the data.json swap and this fix.

## renames-migrations

**Root cause:** Factorio 2.1 renamed three recipe prototypes that existed in 2.0.x. The game ships these as type-scoped JSON migrations in space-age: ore-melting.json maps recipe molten-iron to iron-ore-melting and molten-copper to copper-ore-melting, and tree-seed.json maps recipe wood-processing to tree-seed. PrOBE's migration table (packages/editor/src/core/nameMigrations.ts:28-89) has no 2.1 group, so a 2.0.x blueprint that sets a foundry to molten-iron or molten-copper, or a machine to wood-processing, keeps a recipe name that no longer exists in the 2.1.25 data.json.

What goes wrong after that:

- The `recipeName` schema keyword (bpString.ts:99-100, `!!FD.recipes[data]`) rejects the name. That is only a warning, so loading carries on.
- `Entity.assemblerHasFluidOutputs` and `assemblerHasFluidInputs` (Entity.ts:1740-1752) return false because `FD.recipes[this.recipe]` is undefined, so foundries lose their fluid-output logic.
- The recipe icon and accepted-recipe lookups fail.

The table also cannot hold these renames correctly as written:

- **The `values` map is untyped.** It rewrites any string in any field (nameMigrations.ts:181-182). `molten-iron` and `molten-copper` are still live FLUID names in 2.1 (the fluids are unchanged; only the recipes were renamed). A `values` row would corrupt the 73 fluid-typed signals, infinity-pipe filters and similar in the corpus.
- **The `names` map would also be wrong.** It applies to every `name` field regardless of `type` (lines 174-179).
- **What the game does instead:** the game's migrations are keyed by prototype type ("recipe": [...]), so only recipe references move.

Data diff confirms these are the only 2.0.x-to-2.1 renames that matter. In the new data, removed recipes are exactly [molten-iron, molten-copper, wood-processing], and no item, entity, fluid, tile or signal was removed. Every other space-age migration file has a source name that is absent from the 2.0.x data already, so it does not apply to 2.0.x blueprints. These are biolab.json, cargo-bay-that-allows-inserters-to-remove-items.json, internal.json, jelly-yum-rename.json, shattered-planet.json, tungsten-belt-rename.json and aquilo-tilesets.json. cargo-bay-extractor never appeared in a public release: the changelog lists "Added landing pad unloading bay" under 2.1.7, the first public 2.1. The 2.1 rename is announced in changelog.txt:889 in the 2.1.7 section (lines 726-1395).

Separate problem in another area, found along the way: 2.1 recipes use `categories: [...]` instead of `category`. Examples are iron-ore-melting with categories ['metallurgy'], and tree-seed with ['organic','crafting'], where the old wood-processing had category 'organic-or-assembling'. Entity.ts:399 (`e.crafting_categories.includes(recipe.category || 'crafting')`) and Entity.ts:1423 (`.category === 'crafting-with-fluid'`) still read `category`. This explains the acceptedRecipes histogram drop from 14366 to 5735. It is not caused by renames.

**Fixed-point effects:** Applying the 2.1 recipe migration changes the decoded model of 2 corpus files. test-blueprints/JEPAKAZOL/gleba-mall-5-planets.txt has 15 foundries whose recipe changes from molten-iron/molten-copper to iron-ore-melting/copper-ore-melting. test-blueprints/JEPAKAZOL/nauvis-midgame-science.txt has 1 foundry. Entity, tile, wire and icon counts and the position checksums should not change. That re-recording is driven by the data swap, not by the migration. The entity-accessors histograms (acceptedRecipes) for these 16 foundries are additionally affected by the categories change. basic-builder.txt and the EARN corpus are unaffected by the migration: they contain only fluid-typed or item-typed uses of these names.

## recipe-results

**Root cause:** Nothing in packages/editor/src works out an expected product amount. Every reader takes the raw `ProductPrototype.amount` (falling back to `?? 0` or a default of 1) and ignores every probability field: `probability` in 2.0, and `independent_probability` and `shared_probability{min,max}` in 2.1. It also ignores `extra_count_fraction`, `amount_min`/`amount_max` and `ignored_by_productivity`. In 2.0 this was a hidden, pre-existing bug: a centrifuge showed "1" for uranium-235 with or without probability. Two things made it visible in 2.1.25:

(1) The recycling generator now floors `amount` and puts the remainder in `extra_count_fraction`. See data/recycler/recycling.lua:117-123, `final_amount = math.floor(final_amount / final_probability)`. As a result, 221 recipe results in the new data.json have `amount: 0`. iron-gear-wheel-recycling is `{amount:0, extra_count_fraction:0.5}`; in 2.0 it was `{amount:0.5, extra_count_fraction:0.5}`. The recipe UI now prints "0" for these products.

(2) 2.1 renamed `probability` to `independent_probability` and added `shared_probability`. typed-factorio 3.36.0 (generated for 2.0.75) does not have either field, so no typed reader can see them without a local augmentation.

The game's own formula is in core/lualib/util.lua:633-645 `util.product_amount` ("ref ItemProductPrototype::getExpectedNormalAmount"). Per the 2.1.25 docs (doc-html/types/ProductPrototypeBase.html), the GUI probability is `independent_probability * (shared_probability.max - shared_probability.min)`:

`expected = (amount ?? (amount_min+amount_max)/2) + (extra_count_fraction ?? 0)`, then `*= independent_probability ?? 1`, then `*= (shared.max - shared.min)`.

Note: `amount_max < amount_min` means `amount_min` (ItemProductPrototype docs). The `ignored_by_productivity` default is `ignored_by_stats`, and it is ignored when `allow_productivity` is false.

throughput.ts does not read recipes at all; it only does inserter/belt maths.

**Fixed-point effects:** The pieces are independent of each other and of the other areas. Adding RecipeProduct, productChance and productExpectedAmount to factorioData.ts is additive: recipeResults keeps the same runtime behaviour, and its widened return type stays assignable to ProductPrototype. No headless histogram (entity-accessors) or wire test reads product amounts, so the entity-accessors and wire-switch numbers do not move.

Only the UI text changes, in CreateRecipe and the EntityInfoPanel 'effects' recipe. The display changes for both the old and the new data.json, because probability was already ignored with the 2.0 data. Any Playwright snapshot of those panels will need updating.

The reader keeps the 2.0 `probability` fallback, so it is correct for both the committed 2.0 data and the 2.1.25 data. The one exception is the 2.0 recycling raw amount of 0.5, where it over-reads to 1.0. That stops mattering once the 2.1 data.json is swapped in.

The OverlayContainer fluidbox_index fix is optional, and it changes the pinned fixtures in tests/overlay-container.spec.ts.

Separately: the recipe `category` -> `categories` rename is a different area, but it shares the recipe readers in factorioData.ts. Whoever fixes acceptedRecipes should not route it through recipeResults.

- `packages/editor/src/core/factorioData.ts`: Next to recipeResults (line ~131), add a local 2.1 product type and pure readers, without depending on typed-factorio for the new fields:

export type RecipeProduct = ProductPrototype & {
    independent_probability?: number
    shared_probability?: { min?: number; max?: number }
    probability?: number // 2.0 data.json
}
/** Chance a craft yields this product; GUI 'probability' (ProductPrototypeBase docs). */
export function productChance(p: RecipeProduct): number {
    let c = p.independent_probability ?? p.probability ?? 1
    if (p.shared_probability) c *= (p.shared_probability.max ?? 1) - (p.shared_probability.min ?? 0)
    return c
}
export function productBaseAmount(p: RecipeProduct): number {
    if (p.amount !== undefined) return p.amount
    const min = p.amount_min ?? 0
    return (min + Math.max(p.amount_max ?? min, min)) / 2
}
/** Mirrors core/lualib/util.lua util.product_amount. */
export function productExpectedAmount(p: RecipeProduct): number {
    return (
        (productBaseAmount(p) +
            ((p as { extra_count_fraction?: number }).extra_count_fraction ?? 0)) *
        productChance(p)
    )
}
/** Per-craft expected output including productivity bonus. */
export function productExpectedWithProductivity(
    p: RecipeProduct,
    productivity: number,
    allowProductivity = true
): number {
    const base = productExpectedAmount(p)
    if (!allowProductivity || productivity <= 0) return base
    const ibp = p.ignored_by_productivity ?? p.ignored_by_stats ?? 0
    const extra = (p as { extra_count_fraction?: number }).extra_count_fraction ?? 0
    return (
        base + productivity * (Math.max(0, productBaseAmount(p) - ibp) + extra) * productChance(p)
    )
}

Factorio 2.1.25 adds `circuit_connector` and `circuit_wire_max_distance` (9) to 9 prototypes of 7 types: boiler (boiler, heat-exchanger), pipe, infinity-pipe, pipe-to-ground, heat-pipe, lab (lab, biolab) and land-mine. `getCircuitConnector` (packages/editor/src/core/factorioData.ts:268-383) and `getMaxWireDistance` (factorioData.ts:516-604) have no case for any of these 7 types, so they fall to `default: return undefined` (factorioData.ts:380-381) and `default: return 0` (factorioData.ts:602-603).

What the user would see once the new data.json is in place:

- A blueprint that wires any of these entities throws "Could not find the wire connection point!" (WiresContainer.ts:183-185, from `Entity.getWireConnectionPoint` at Entity.ts:1755-1781) inside `initBP`. This is the same way the whole blueprint was lost in the splitter bug, #186.
- Their wire reach is 0, so wires to them are drawn at alpha 0.3.
- PaintWireContainer cannot attach a wire to them.

The connector data comes in three shapes, so one arm is not enough:

1. **One definition, not an array.** lab, biolab, land-mine. In the API this is `CircuitConnectorDefinition`, the same as reactor. land-mine has `points` only and no `sprites`.
2. **A 4-entry array indexed by facing N, E, S, W, read as `[dir/4]`.** boiler, heat-exchanger, pipe-to-ground. The API types these as a 4-tuple, and the Lua offsets follow N, E, S, W (core/lualib/circuit-connector-generated-definitions.lua:1057-1066, 1091-1100).
3. **A 16-entry array indexed by which neighbours the entity connects to, not by direction.** heat-pipe, pipe, infinity-pipe.
    - heat-pipe: the API documents the order as a bitmask with N=1, E=2, S=4, W=8. Index 0 is single, 1 is ending_up, 2 ending_right, 3 corner_right_up, 5 straight_vertical, 10 straight_horizontal, 15 cross (prototype-api.json HeatPipePrototype.circuit_connector; Lua :1102-1119).
    - pipe: the API only says "exactly 16 elements" and gives no order. The pipe Lua entries (:1068-1088) follow the same bitmask: the vertical-shaped indices 1, 4 and 5 all use variation 12, and the horizontal-shaped indices 2, 8 and 10 all use variation 26.
    - infinity-pipe inherits PipePrototype, and its connector data is byte-identical to pipe's.
    - Reading `[dir/4]` for these 16-entry types would compile but would always return the single/ending variants. Each needs the entity's 4-neighbour connection mask, which the editor already computes for drawing: `getFluidConnections` (spriteDataBuilder.ts:379) and `getHeatConnections` (spriteDataBuilder.ts:389) return `[N, E, S, W]`. The order is confirmed by draw_heat_pipe at spriteDataBuilder.ts:1660-1700 and draw_pipe at 2122-2207: `conn[0] && conn[2]` gives straight_vertical and `conn[0] && conn[1]` gives corner_right_up.

There is a second problem in the code that redraws after a neighbour change. A pipe's or heat-pipe's connector moves when its neighbours change. EntityContainer.ts:443-448 redraws neighbouring sprites but calls `wiresContainer.update` only for `transport-belt`. Without a change there, the wire ends would stay at the old connector position.

Third, the typing. typed-factorio 3.36.0 (2.0 API) declares neither `circuit_connector` nor `circuit_wire_max_distance` on BoilerPrototype, PipePrototype, PipeToGroundPrototype, HeatPipePrototype, LabPrototype or LandMinePrototype. The new arms need a local intersection type, not the bare prototype casts the existing arms use.

landing-pad-unloading-bay (type cargo-bay, new in 2.1) declares no `circuit_connector` and no `circuit_wire_max_distance`. Neither switch needs an arm for it.

**Fixed-point effects:** These numbers come from my plain-JS copy of the two switches (sim.js); I did not run the repo's own test suite (vp test).

**On the new 2.1.25 data, current switches:** both completeness tests fail. 9 entities fall to `default:` in getCircuitConnector, and 9 return a distance of 0 instead of 9 in getMaxWireDistance.

**On the new data, with the proposed arms:** 89 of 89 connector-declaring entities are handled and 93 of 93 distances match. The old control test fails at that point, because pipe is now given a connector and a reach of 9. That is why the control has to move to beacon or underground-belt.

Blueprints that wire these entities stop throwing "Could not find the wire connection point!" in initBP and now draw their connector sprites. land-mine draws no connector sprite because it has none.

## sprites-new

**Root cause:** The exporter (packages/exporter/src/setup.rs) turns every quoted "*.png" string in data.json into data/output/<same path>.basis (IMG_REGEX at setup.rs:248/404, out_path at :263/:418). The committed .basis set (3060 files) exactly matches the 2.0 data.json, which references 3060 PNGs, so nothing is missing for 2.0. The 2.1.25 data.json references 3229 distinct PNGs. 344 of them have no .basis, 175 existing .basis are no longer referenced, and at least 28 still-referenced .basis files are stale because the game changed the PNG under the same path (their dimensions no longer match). Three things in the exporter get in the way of a clean refresh: (1) it never deletes .basis files that are no longer referenced, so the 175 orphans would stay; (2) output/metadata.json is gitignored (.gitignore:5) and missing, so old_metadata is empty and a real run re-encodes all 3229 files, not just the 344 new ones; (3) the metadata skip in compress_next_img (setup.rs:~508) checks only the input PNG's length and mtime, never whether out_path exists. All 3229 referenced PNGs exist in the local game install, including the new **recycler** mod directory, so the encode inputs are all there.

**Fixed-point effects:** Regenerating sprites does not change any headless or vitest result in the core model, because sprites are only loaded through globals.getTexture in the browser. It does affect the browser and Playwright sprite suites (tests/sprite-data.spec.ts, tests/sprite-generation.spec.ts) and any visual snapshots. With the new data.json but the old .basis set, the 2.1-reworked entities would request missing files: assembling-machine-1/2/3, oil-refinery, chemical-plant, centrifuge, foundry, pump, asteroid-collector, flamethrower-turret, heat-exchanger, burner-mining-drill (flipped), pumpjack, rocket-silo, landing-pad-unloading-bay and the frozen-foundation tile. The 28 dimension-stale files would draw wrong sub-rects (AM shadows and pipes, pumpjack shadow, stone-path/concrete/foundation u-pieces, agricultural-tower base). Swapping data.json and regenerating the sprites must therefore land in the same commit. After the regen and the orphan prune, the output holds 3229 .basis that map one-to-one onto data.json refs, and **quality**/graphics loses its recycler entries in favour of the new **recycler** directory. ## shape-diff

**Root cause:** The 2.1.25 data.json changes the shape of several prototype fields the editor reads. The tests only catch two of these (they cause (a) and part of (b)). Several other changes crash or blank the rendering, and the headless tests never reach them.

1. **Recipe categories.** RecipePrototype.category was removed and RecipePrototype.categories (string[]) replaced it. The changelog says "Removed RecipePrototype::category, additional_categories. Use RecipePrototype::categories instead", and 0 of 656 recipes still have `.category`. The machines' crafting_categories also lost all the "x-or-y" composite categories. Entity.acceptedRecipes reads `recipe.category || 'crafting'`, so every recipe now counts as 'crafting'. Assemblers accept all 656 recipes and every other crafter accepts 0. That is the acceptedRecipes 14366 -> 5735 move: 14366 crafting entities in the corpus, and only the assemblers still come out non-empty. The crafting-with-fluid check in pasteSettings never matches either.

2. **Removed recipes.** molten-iron and molten-copper are gone and nameMigrations has no 2.1 group. 16 corpus entities keep a recipe that no longer exists. recipeSupportsModule reads FD.recipes[recipe].allowed_module_categories on undefined, which gives the 16 acceptedModules throws.

3. **Chest circuit connector.** container, logistic-container, infinity-container and proxy-container changed circuit_connector from a single object to a 1-element array. getCircuitConnector still returns the raw field for these types. Entity.getWireConnectionPoint tests `cc?.points`, which is undefined on an array. So WiresContainer throws "Could not find the wire connection point!" for every wired chest: 147 corpus blueprints, 5586 wired chest entities. The chest connector sprite also stops drawing. This is not covered by any headless test.

4. **Graphics fields moved.** Three `need()` calls in spriteDataBuilder now throw:
    - generator: horizontal_animation/vertical_animation moved to pictures.{north,east}.animation. This hits every steam-engine and steam-turbine.
    - logistic-container: animation moved to robot_door.animation. This hits all 5 logistic chests.
    - pumpjack: base_picture moved to graphics_set.working_visualisations[0].{dir}_animation.

    Separately, assembling-machine-2/3 fluid_boxes[].pipe_picture.{dir} became {layers:[...]}. The `!pipePic.filename` guard drops these pipe sprites without any error.

5. **hide_connection_info moved.** It moved from fluid_box to fluid_box.pipe_connections[]. OverlayContainer only checks the fluid_box level, so pipes, storage tanks and pipe-to-ground now get fluid arrows, and the hidden input side of pumps and valves is drawn.

6. **Blueprint format.** The schema forbids decider_conditions.else_outputs (additionalProperties:false). There are 80 warnings on the current corpus, and 7 corpus blueprints are already stamped 2.1.12. The editor still stamps 2.0.45.

The rest of the schema diff is not read by the editor: fuel_category -> fuel_categories, tool -> item for science packs, result probability -> shared_probability/independent_probability, quality effects divided by 10, the defines.inventory/control_behavior renames, utilityConstants and guiStyle changes, and tile transition layout. It needs no change.
